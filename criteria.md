# Acceptance criteria — FitFindr

Five criteria that say what "working" means for this agent, written in unit 3
**before** any results existed.

An acceptance criterion names a target: a number, a count, a rate, or something
a person could plainly observe. *"The agent handles errors"* is an opinion.
*"When search returns nothing, the agent stops before calling the second tool,
in 5 of 5 tries"* is a criterion.

Under each one, write a sentence or two on **why that target** and not a
stricter one. A reason that says something about your tools, your loop, or the
data earns credit; *"80% seemed reasonable"* does not.

> Missing your own targets next unit costs you nothing. Setting a target so
> easy you can't miss it does.

**Two are written for you. You write three.**

---

## 1. A matching query completes all three tools

Given a query that matches at least one listing, the agent completes all three
tool calls and returns a fit card — in at least 4 of 5 tries.

**Why this target:**

The successful path includes model calls in suggest_outfit and create_fit_card. Those calls can fail or return unusable output even when search finds a listing. Requiring four successful runs out of five allows one failure while still requiring the complete workflow to work reliably.

---

## 2. An impossible query stops before the second tool

Given a query that matches no listings, the agent stops before calling
`suggest_outfit` and returns a message naming what to change — 5 of 5 tries.

**Why this target:**

An empty search result is handled by a condition in my planning loop before outfit generation. This decision does not depend on model output, so it should stop correctly and suggest changing the description, size, or budget in all five trials.

---

## 3. The selected item stays the same across tool calls

Given a query that returns at least one listing, the first search result, session["selected_item"], and the new_item received by suggest_outfit must have identical field values in 5 of 5 trials. Each trial will record these values so they can be compared.

**Why this target:**

Passing the selected item between functions is controlled by my code, not the model. All five trials should match because changing the item would cause the outfit suggestion to describe a different listing.


---

## 4. The fit card includes accurate details in a short caption

Given a selected listing and a non-empty outfit suggestion, the returned fit card must contain two to four sentences, include the selected listing's exact title once, and mention its price and platform exactly once each, in at least 4 of 5 trials. Each trial will use a different listing. A trial passes only if all these conditions are met.

**Why this target:**

The caption is generated by a model, so its wording and sentence structure can vary. Four successful trials out of five allow an occasional formatting or instruction-following failure while requiring most captions to meet the specification. The item, price, and platform will be checked against the listing data.


---

## 5. A saved wardrobe is used in a separate run

Given a wardrobe containing a uniquely identified item added by the user, save the wardrobe and end the program. Start a separate process without entering the wardrobe again, then run a query that matches a listing. The saved item's ID and all its field values must appear in both the loaded wardrobe and the wardrobe passed to suggest_outfit, in 5 of 5 trials. Each trial will use a different added item.

**Why this target:**

My style-memory feature should preserve wardrobe data between runs. Saving and loading are controlled by local code, so all five trials should preserve the item exactly. Checking the input received by suggest_outfit confirms that the saved wardrobe reaches the tool, rather than merely remaining in a file.
